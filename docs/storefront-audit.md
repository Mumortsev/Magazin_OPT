## Архитектура исходного проекта и целевая схема

- `storefront/` уже содержит Vite/React/TypeScript, Lucide, адаптивный интерфейс, демонстрационный каталог, сортировку, фильтры, плитку и список. `src/data.ts` хранит демонстрационные цены и остатки. `src/App.tsx` сохраняет заявку файлом, `src/cart.tsx` хранит корзину в браузере. GitHub Actions публикует статическую витрину при push в main.
- `frontend/` — самостоятельный клиент Telegram и браузера. `app.js`, `catalog.js`, `cart.js` и `api.js` обеспечивают каталог, корзину, оформление, профиль с заказами, Telegram/WhatsApp и уведомления. Старый worker и манифест обслуживают существующих клиентов.
- `backend/api/database.py`, `models.py` и `schemas.py` — асинхронный SQLAlchemy, SQLite по умолчанию, категории и подкатегории, галерея, товары, заказы и позиции. Покупатель представлен контактами заказа, Telegram ID или номером WhatsApp. Отдельной модели пользователя нет. Остаток выражен в упаковках. NULL означает, что количественный остаток не ведётся. Позиция хранит количество упаковок и единиц, цену и сумму.
- `backend/api/notifier.py` использует `notify_new_order` для Telegram/PDF и запуска Web Push/FCM. `pywebpush` и VAPID пригодны для нового транспорта, обработка 404/410 уже заложена. Текущий путь через BackgroundTasks теряется при остановке процесса. FCM остаётся компонентом старого проекта.
- Целевая схема — браузер → Vite-сайт и React-админка → версионированные публичные и защищённые API FastAPI → существующие таблицы каталога и заказов плюс таблицы сотрудников, сессий, журнала, CMS и доставки. БД → очередь доставки → Web Push и SMTP. БД → SSE → открытая админка. Telegram продолжает работать через совместимый API и отдельный маршрут приложения.

## Риски и миграция

| Область | Риск | Решение |
|---|---|---|
| Доступ к БД через старые маршруты | Список, детали и изменение заявок, мутации каталога и импорт не защищены. Проверка Telegram ID принимает знание ID. Практически открытый CORS с credentials. | Новые маршруты защищать ролями, origin и CSRF. Старые административные маршруты закрыть для произвольных запросов, оставить серверный канал бота, сохранить покупательские маршруты. До совместного запуска проверить способы авторизации профиля Mini App. |
| Отладка и загрузки | Маршруты отладки и миграций доступны без нормальной авторизации. Импорт формирует путь из имени клиента, хранит куски в памяти. Push принимает произвольный endpoint. В контейнере нужно проверить порядок монтирования статических файлов и PDF. | Убрать опасные маршруты из production, ограничить загрузки и разбор файлов, не использовать клиентские пути, разрешить только доверенные Web Push хосты, проверить маршрутизацию SPA и медиа. |
| Приватность и вывод | Данные покупателя и ответы импорта вставляются через innerHTML. У заказов Telegram/WhatsApp отдельные слабые места в проверке идентичности, а уведомления могут содержать лишние данные. | React-вывод, минимум данных в Web Push, HMAC Telegram initData или отдельный доверенный канал для операций, где нужна идентичность. |
| Транзакции | Старая проверка количества идёт по строкам, допускает дубликаты товара, затем списывает склад отдельной фазой. Денежные расчёты проходят через float. Некоторый недоступный товар может исчезнуть из заявки. | Для веба проверять всю корзину, использовать Decimal и атомарное изменение остатка, запрещать повторяющиеся строки, сохранять ключ идемпотентности и отпечаток заявки. |
| Статусы и ответственные | В БД встречаются две группы статусов и текстовые коды менеджеров. | Читать `new` как «Новая», `processing` как «В работе», `accepted` как «Подтверждена», `shipped` как «Отправлена», `completed` как «Выполнена», `cancelled/rejected` как «Отменена». Существующие значения сохранить. Связь с веб-сотрудником хранить отдельно от M1–M4. |
| Импорт | При ошибке строки rollback может откатить предыдущие успешные строки при уже увеличенных счётчиках. Некорректная цена становится нулём. | Переиспользовать форматы и сопоставление колонок, показывать корректные предварительные счётчики и ошибки, применять план повторно с проверкой актуальности в одной транзакции. |
| Миграции | Текущий SQLite startup запускает не только DDL, но и перегруппировку каталога. | Явная добавочная миграция, снимок SQLite и медиа, пробный прогон на копии с проверкой количества строк и исторических статусов. Откат приложения без удаления новых таблиц. |
| Публикация | Merge в main запускает GitHub Pages. Реальная веб-сессия и SSE требуют маршрутизации API и админки с одного origin. | Локальная ветка, проверка на тестовой базе. Для боевого запуска отдельно настроить HTTPS, постоянное хранилище, маршрутизацию, VAPID и SMTP. |

## Порядок работ

1. Аудит и карта соответствий из этого документа.
2. Адаптивная витрина и веб-админка с настоящими контрактами API, ясными количествами и доступными формами.
3. Добавочные миграции, публичный каталог, реальная заявка, защищённые сессии, роли, операции каталога, импорт, аналитика и CMS.
4. Атомарный захват заявки, история, SSE, сохранённые задания Web Push и SMTP, журнал и повторы.
5. Сборка и проверки на отдельной базе с покупателем, двумя менеджерами, администратором и сохранёнными данными Mini App. Проверка мобильного экрана, клавиатуры и доставки через настроенные тестовые каналы. Публикация только после отдельного разрешения.
